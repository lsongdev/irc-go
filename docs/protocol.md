# 协议实现说明

## 规范基线

实现以 [RFC 1459](https://www.rfc-editor.org/rfc/rfc1459) 和 [RFC 2812](https://www.rfc-editor.org/rfc/rfc2812) 为核心基线，并兼容 [IRCv3 message tags](https://ircv3.net/specs/extensions/message-tags) 的解析与编码。

严格性体现在协议边界，而不是宣称实现所有历史扩展：

- 编码消息总以 `CRLF` 结尾，总长度不超过 512 字节。
- 命令统一为大写，最多 15 个参数；包含空格或空字符串的最后参数使用 trailing 形式。
- 拒绝内嵌 NUL、CR、LF 的消息，验证昵称与频道名称。
- 标签值按 IRCv3 规则转义；标签按键名排序，使输出可重现。
- 昵称与频道索引使用 RFC 1459 casemapping，因此 `[`/`{`、`]`/`}`、`\`/`|`、`^`/`~` 等价。
- 数字回复均包含目标昵称，服务端消息包含服务端前缀，用户事件包含完整 `nick!user@host` 前缀。

## 注册与能力协商

客户端可以按 IRC 标准发送可选的 `PASS`，再发送 `NICK` 和 `USER`。服务端仅在三项条件满足、且 `CAP` 协商结束后发送 `001`–`005` 与 MOTD。

当前没有声明 IRCv3 capability；`CAP LS` 返回空列表，`CAP REQ` 返回 `NAK`。消息标签仍可由协议库解析，但服务器不会在未协商 capability 时转发客户端标签。

## 状态模型

服务端状态由单一互斥区串行变更，网络写入进入每连接的有界队列。这保证昵称、频道成员和权限变更是原子的，同时慢连接不会阻塞整个服务器；队列耗尽的连接会被关闭。

频道默认模式为 `+nt`：外部用户不能向频道发送消息，只有频道管理员能修改主题。首个加入者获得 `+o`。如果最后一个管理员离开，服务端会提升一名现有成员，避免频道永久失去管理能力。

所有会话数据都保存在内存中。IRC 连接、临时频道、away 状态和成员关系本身是瞬态数据，因此当前不需要 SQLite。若应用需要账号、频道注册或历史记录，应在上层订阅消息并实现独立存储，而不是把持久化耦合到线协议状态机。

## 明确边界

本实现面向单服务器聊天。以下功能有意不包含：

- 多服务器拓扑以及 `SERVER`、`SQUIT`、netsplit 同步；
- services、SASL、账号注册与持久化频道；
- ban/invite exception 列表、DCC、文件传输和历史回放；
- TLS 证书管理（可以把 `tls.Listener` 交给 `Serve`）；
- 非 UTF-8 文本转码。

服务端通过 `005` 只公布实际支持的 `CHANTYPES`、`CHANMODES`、`PREFIX`、`CASEMAPPING` 和 `NICKLEN`，客户端不应假设未公布的扩展存在。
